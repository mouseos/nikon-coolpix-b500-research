# ファームウェア改変の可能性 (署名検証)

## 結論

更新経路に暗号学的な署名検証はない。
ファームウェアファイルの確認は、先頭のマジック文字列の比較と、
書き込み後の読み戻し比較だけである。
したがって、改変した firmware.bin を作れば、署名の壁には当たらない。
ただし実機への書き込み検証はしていない。文鎮化の危険は残る。

## 根拠 1: ファイルを開くときの確認はマジック文字列だけ

本体イメージの更新処理 (関数先頭 0x806EF2E4) は、
SD カードの `D:\firmware\firmware.bin` を開き、先頭 0x20 バイトを読む。
その後 0x806EF388 で memcmp (0x8006F1E0) を呼び、
文字列 `SUNP BURN FILE` と 14 バイトだけ比べる。
一致しなければ `not SUNP BRN file` と表示して中断する。
ハッシュ計算や署名検証の呼び出しは、この確認の前後にない。
逆アセンブルは evidence/disasm-magic-check.txt。

## 根拠 2: 書き込み後の verify は読み戻し memcmp

CardUpdate の verify 関数 (0x80896EE8) の処理は次のとおり。
命令を追った結果である (evidence/disasm-verify-fw.txt)。

1. フラッシュから現在のファームウェアサイズを取得し、
   期待サイズより小さければ `Fw verify failed: size unmatch` で失敗。
2. 書き込んだサイズ分のバッファを確保する。
3. 記録媒体ごとの読み出し関数 (NAND / eMMC / SPI 等への分岐表経由) で、
   書き込んだ内容を丸ごと読み戻す。
4. memcmp (0x8006F1E0) で元のデータと読み戻しを全量比べる。
   一致すれば `[CardUpdate]verify fw success.`、
   違えば `[CardUpdate]verify fw failed :%d.` と、
   両バッファの先頭 0x100 バイトのダンプを出す。

この関数が呼ぶのは、メモリ確保、読み出し、memcmp、表示だけである。
公開鍵、ハッシュ、署名といった検証材料は使っていない。

## 根拠 3: リソースファイルの verify も同じ方式

HDR3 の校正ファイル一覧に対する verify も、書き込み後の
読み戻し比較である (`[CardUpdate]verify res file %s success.` /
`failed` の表示が、サイズ確認と読み戻しの後に並ぶ)。

## 改変するときに守る必要がある整合性

署名はないが、形式の整合性は必要になる。

- 先頭ヘッダの全体長フィールド (0x10) はファイル長と一致させる。
- 各領域のオフセット (HDR1 / HDR2 / 本体 / HDR3) をずらさない。
  サイズを変える場合はオフセット表も直す必要がある。
- FAT イメージを書き換える場合は、BPB の総セクタ数と実サイズを
  一致させる。終端位置が次の領域の開始と一致するのが前提の構造である。
- HDR3 一覧の校正ファイル (COLD.BIN、欠陥画素データ) は、
  更新時に退避・復元される前提の名前なので、消したり改名したりしない。

## 未確認の点

- ブートローダ側イメージ (0x200〜) にも CardUpdate の文字列一式が
  含まれており、同じ方式とみられるが、ブートローダ側の verify 関数の
  命令までは今回確定していない。実機の更新はブートローダ側が担う
  可能性があるため、ここは未確認として残す。
- 実機で改変ファームウェアを書き込んだ検証はしていない。
  書き込み自体は通常の更新手順 (SD カード経由) で行われる設計だが、
  失敗時の復旧手段は確認できていない。
