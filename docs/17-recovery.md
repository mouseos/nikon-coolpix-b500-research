# 17 ファームウェアを壊した場合の復旧手段

## 結論

復旧の仕組みは、壊れた場所ごとに段階がある。本体ファームウェアが起動する範囲なら公式の更新で戻せる。本体が起動しなくても、ブート領域に独立した書き込みプログラム (Card ISP) が入っていて、SD カードから書き直せる設計になっている。ブート領域自体を壊した場合は、基板を開けてフラッシュへ直接書くしかない。

通常の更新が書き換えるのは、リソースファイル、本体コード、DRAM パラメータの3つだけである。ブート領域は更新の対象に入っていない。毎回書くか差分だけ書くかという以前に、ブート領域はそもそも書かれない。

## 第1段階: 公式のカード更新

本体ファームウェアが起動する状態なら、公式アップデーターの firmware.bin を使って上書きできる。更新の検査はマジックの比較だけで署名検証がない (docs/02)。改造で壊しても、起動さえすれば正規のイメージで戻せる。

書き込みは、本体ファームウェアが自分のプロセス内で行う。本体イメージの中に Card ISP と同じ更新モジュールが入っていて、UI の更新処理がそれを直接呼ぶ。再起動してブート側のプログラムに任せる方式ではない。命令レベルで確認した呼び出しの流れは次のとおり。

1. UI ハンドラが `D:\firmware\firmware.bin` を検査する。マジック「SUNP BURN FILE」の比較に加え、本体イメージ先頭付近の「VQSD_BRN:」署名から版数を読み、機種コード「KP35500」が一致するファイルだけを先に進める (VA 0x806EF2E4)。
2. FW_FirmwareUpdate_Proccess (VA 0x806EF8A0) が更新モジュールの入口 (VA 0x80895BF4) を呼ぶ。
3. 更新モジュールはファイルをメモリへ読み (VA 0x80894E48)、ヘッダを解析し (VA 0x80895318)、更新本体 (VA 0x80897EA0) を実行する。

更新本体の処理は、バックアップ対象ファイルの退避、フラッシュのフォーマット (updateMode が 0 のとき。対象は予約ドライブ rsvA / rsvB / DrvC)、リソースとファームウェアの更新、バックアップの復元、の順である。リソースとファームウェアの更新 (VA 0x808977DC) の中身は次の3つで、全て対象が存在すれば無条件に書き込む。現在のフラッシュの内容と比較して、同じなら省く処理はない。

- リソースファイル。内蔵 FAT (A: RO_RES、B: USER_RES) の中身を更新する。
- Firmware。本体コードの領域。書き込むデータは更新ファイルのヘッダ [0x1C] が指すオフセット (本体イメージの開始位置) から取る。書き込み後、読み戻して元データと比較する検証が付く (VA 0x80896EE8)。
- DRAM パラメータ。更新ファイルのヘッダ [0x28] が指すオフセットから取る。

ブート領域のオフセット (0x200) を指す書き込みは、この流れのどこにもない。

## 第2段階: ブート領域の Card ISP

ブート領域 (0x200〜0x93400) には、本体ファームウェアとは独立した「iCatch Card ISP」が丸ごと入っている。第1段階と同じ更新モジュールの単体版である。文字列と命令から確認できた動作は次のとおり。

- SD カードをマウントする。
- 更新前に、現在のファイルを SD の `D:\IBACKUP` へバックアップする (ファイル名は %04x.BIN 形式)。
- リソースファイル、本体コード、DRAM パラメータを書き換える。対象は第1段階と同じ3つで、ブート領域自体は含まない。
- 終わると自動で電源を切る。
- コンソールも持ち、`isp <ファイル>` でカード上の .BIN / .BRN から書き込み、`boot <ファイル>` でカード上のイメージから起動できる。

入り方は、ispBootMode という値で決まる (ispBootModeGet、ログ出力「ispBootMode:%d」)。この関数はブート側だけにあり、本体イメージにはない。通常の更新は第1段階のとおり本体側で完結するので、ispBootMode は通常更新では使われない。

本体が起動しない状態からの入り口として、B500 のブートイメージには、カード上のファイル名を検出して自動で更新を始める仕組みはない。更新ファイル名にあたる文字列 (SPHOST.BRN のような固定名) がブート領域に存在しないためである。残る入り口は、ispBootMode の値があらかじめ立っていることと、コンソールの `isp` コマンドである。ispBootMode の値がどこに保存され、誰が立てるかは、更新ファイル内のコードからは特定できなかった。

同じ Card ISP 系の EKEN H9 では、更新ファイル (SPHOST.BRN) をカードに入れて電源を入れると自動で更新が始まる手順が公式に案内されていた。B500 のブートは別ビルド (docs/16) で、ファイル検出の入り口自体が無いので、この入り方は使えない。

なお、ブート領域とは別に、フラッシュの予約領域には Boot / FW0 / FW1 と呼ばれる小さなシステム情報レコードが3重に置かれている。本体イメージには、そのチェックサムを検証し、壊れたコピーを正常なコピーから書き直す修復処理がある (VA 0x804DD17C、「Update Boot Area %d」等のログはこの処理のもの)。これはブートイメージ (約600KB) そのものの書き換えではない。

## 第3段階: フラッシュへの直接書き込み

ブート領域まで壊した場合は、外部から書くしかない。ブート領域のコードには SPI フラッシュの扱い (Winbond のアドレスモード切替、SPI_RAW.BIN、spiUpdateDrampara) が含まれ、更新イメージ自体がフラッシュの生レイアウト (SUNP BURN FILE) である。基板上の SPI フラッシュにプログラマ (クリップと CH341A 等) でイメージをそのまま書けば、原理的には全領域を復旧できる。フラッシュの型番と実装形態は更新ファイルには現れないので、実物の基板で確認するしかない。

## 改造でブート領域は壊れるか

機能追加や自作ファームウェアの改造対象は、本体コードと FAT のリソース領域である。docs/03 から docs/15 で扱った改造 (RAW の開放、HDR の開放、ISO や動画の制限変更、UI の差し替え等) は全てこの範囲で収まり、ブート領域を書き換える必要はない。

通常の更新も Card ISP の更新も、ブート領域を書き換えない。したがって、純正ブートを残した自作イメージを通常の手順で書く限り、書き込み中の中断でブート領域が壊れる経路もない。壊れるのは次の場合に限られる。

1. ブート領域自体を改造した場合。
2. コンソールの raw 書き込み等、更新手順の外の手段でブート領域に書いた場合。
3. 他機種のイメージを書いた場合。本体の検査は機種コード (KP35500) の不一致で先に進めないが、検査を通らない手段で書けば、本体コードと DRAM パラメータが自機向けでなくなり起動しなくなる。

安全線は、自作イメージでブート領域と末尾の DRAM パラメータ (DRAMPAR) を純正のまま残し、改造を本体コードとリソースだけに閉じることである。そうすれば、本体が起動しなくなっても Card ISP の受け口が残る。

## 注意点

- 更新手順はブート領域を書かないが、ブート領域自体を改造すると、第2段階の受け口 (Card ISP) ごと失う。ブート領域に触る改造だけは復旧手段が第3段階しか残らない。
- プラットフォームには PC から USB で書く工場用ツールの存在も確認している (EKEN H9 の配布物に USB_CAM.dll や SPC.BIN が同梱)。B500 がその経路に対応するかは、更新ファイルからは判断できない。
