# 自作 UI の可能性

## 結論

UI はデータ駆動である。画面の部品、画像、文言はすべて
リソースファイル側にあり、コードはそれを読み込んで表示する。
リソースの差し替えによる見た目の改変はできる。
新しい画面や操作そのものを足すには、MIPS コード側の改変が要る。

## 根拠 1: 画面レイアウトは UIDATA.BIN の中にある

RO_RES/UIDATA.BIN は `FIF1` というコンテナで、中に画面ごとの
レイアウト部品が名前とサイズの表で並ぶ。実読した部品名は次のとおり。

- UIBOOT00.BIN (起動)
- UIGENERA.BIN (一般)
- UIMODESE.BIN (モード選択)
- UIOPEN.BIN (オープニング)
- UIPLAYBZ.BIN (再生)
- UISETUPO.BIN (セットアップ)
- UIVIDEO.BIN (動画)
- UIVIEW.BIN (撮影表示)
- UIWIFI.BIN (Wi-Fi)

ドライブ B (USER_RES) 側にも UIDATA.BIN と UIPAIRED.BIN があり、
ユーザー側で書き換わる UI データの置き場になっている。

## 根拠 2: 画像と文言もリソース側にある

- 画面の背景やメニュー画像は RO_RES の JPG ファイル群。
- アイコンとフォントは ICON や SFN 形式のファイル群。
- 文言は TXT フォルダの各国語テキスト (UTF-16LE) と、
  offset テーブルで位置を引く形式である。

署名検証がない (docs/02) ため、FAT イメージを再構築して
差し替えたファームウェアを書くこと自体は、形式の整合性を
守れば可能である。

## 注意: 文言テーブルは他機種と共有

ENG.txt などの文言テーブルには、B500 にはない機能の文言も
含まれている (他機種と共有のテーブルのため)。
文言があることだけを根拠に「B500 にその機能がある」とは
判断できない。この調査では、文言の存在は機能の根拠に使わず、
不在の確認と、選択肢の実内容の確認にだけ使った。

## 未確認の点

- UI*.BIN のバイナリ形式の完全な解読は未実施である。
  部品の差し替えはできても、レイアウトの自由な編集には
  形式の解析が先に要る。
- 新しい画面遷移や操作を追加するコード改変は、規模の見積もり
  自体をしていない。
